# Runbook

Operating Menu Studio: deploying, and what to do when something breaks.

## Deploying

`main` deploys to staging automatically. Production deploys from a published release (or a manual
run of the workflow) and waits for a reviewer on the `production` GitHub environment.

Both workflows do the same things in the same order:

1. Build `apps/api` and `apps/worker` images and push them to ECR, tagged with the commit.
2. Apply database migrations.
3. `cdk deploy --all` with that image tag.
4. Build the owner app against the deployed API URL and sync it to S3 — hashed assets first with a
   one-year cache, then `index.html` with `must-revalidate`, then invalidate `/index.html`.
5. `GET /health`.

### First-time setup in a new AWS account

```bash
cd infra
pnpm exec cdk bootstrap aws://<account>/<region>
pnpm exec cdk deploy MenuStudio-staging-Secrets -c environment=staging
```

Then fill in the secret's placeholder fields (every one reads `REPLACE_ME`) in the console or with
`aws secretsmanager put-secret-value`. `PRINT_TOKEN_SECRET` is generated by AWS — leave it alone.
Deploy the rest once the secret is real:

```bash
pnpm exec cdk deploy --all -c environment=staging
```

To attach real domains, pass the `domain` context object (`zoneName`, `webHost`, `menuHost`,
`apiHost`, `cloudfrontCertificateArn` in us-east-1, `regionalCertificateArn` in the app region).
Without it the distributions keep their `*.cloudfront.net` names and everything still works.

### Rolling back

- **A bad API or worker image**: ECS's deployment circuit breaker rolls the task set back on its
  own. To force it, redeploy the previous tag:
  `pnpm --filter @menu-studio/infra exec cdk deploy MenuStudio-production-Api -c environment=production -c imageTag=<previous>`
- **A bad owner-app build**: re-run the deploy workflow on the previous commit. The S3 bucket is
  versioned, so the old objects are still there if you need to restore one by hand.
- **Published QR menus are unaffected by a rollback.** They are static files that were already
  written to S3; nothing at request time depends on the API.
- **A bad migration**: migrations are forward-only. Write a new one that reverses the change.

## When something breaks

### Exports are stuck at "queued"

The worker consumes the `export` queue through pg-boss.

1. `GET http://<task>:5324/health` on the worker task, or check the ECS service has running tasks.
   The `NoRunningTasks` alarm fires when it does not.
2. Check the queue depth: `select name, state, count(*) from pgboss.job group by 1, 2;`
3. If the worker is up and the queue is draining but slowly, exports are simply busy — each one
   launches a Chromium context and `EXPORT_CONCURRENCY` defaults to 2. Scale the service out.
4. If tasks are crash-looping, it is almost always memory: Chromium needs the 1 GB shared memory
   segment the task definition sets, and 4 GB of task memory in production.

### An export fails with "fonts did not load"

The export refuses to render rather than shipping a menu in a fallback font. Either the mirrored
fonts are missing from the image (`pnpm fonts:mirror` runs at image build time) or the print route
could not reach them. Check the worker logs for the failing pairing id, then rebuild the image.

### A PDF's fonts are not embedded

Run the check the e2e suite runs:

```bash
pnpm exec playwright test print-geometry
```

If a font comes back as `Type3`, a **variable** font instance has been mirrored instead of a static
one. `packages/design-system/scripts/mirror-fonts.ts` requests the files with an old Chrome user
agent precisely to get static instances; check that script first.

### A published menu is stale

HTML is served with `s-maxage=5`, so a republish is visible within seconds. If it is not:

1. Confirm the publish job finished: `select status, error from published_menus where id = ...`.
2. Confirm the objects are in the menu bucket with the expected `Cache-Control`.
3. Only then invalidate CloudFront. Invalidating is a symptom-level fix; the cause is usually a
   failed publish job.

### The API returns 503 from an AI route

`ANTHROPIC_API_KEY` is missing or the upstream call failed. The route returns
`ai_not_configured` or `ai_unavailable` with `retryable: true`. Everything that does not involve the
model keeps working, which is deliberate: an owner can still edit, export and publish.

### A menu overflows its pages

The overflow engine reduces density, then font size to its floor, then rebalances columns, then adds
a page if the brief allows. When it cannot fit, it flags the version rather than silently shrinking
text below 8.5 pt. The fix is editorial (shorter descriptions, fewer items, more pages), and the
editor surfaces it.

## Data

### Backups

Supabase's own point-in-time recovery covers the database. The S3 buckets are versioned with
30-day noncurrent expiry, so an overwritten publish can be recovered for a month.

### A GDPR request

- Export: `GET /account/export` returns everything the account owns as JSON. The Settings screen
  calls it directly.
- Delete: `DELETE /account` with `{"confirm": "DELETE"}`. Organizations the user solely owns are
  deleted with their menus, published sites and exports.

## Development

### Reset the local stack

```bash
pnpm db:reset      # drop, migrate, reseed
```

### Regenerate visual baselines

Baselines are Linux-only because text metrics differ per platform. Generate them in the same image
CI uses:

```bash
docker run --rm -it -v "$PWD":/w -w /w mcr.microsoft.com/playwright:v1.63.0-noble \
  bash -c "corepack enable && pnpm install --frozen-lockfile && pnpm fonts:mirror && pnpm e2e --update-snapshots"
```

The visual project skips itself anywhere else, so a macOS run is not a false pass.

### Run the extraction eval

```bash
pnpm db:start && pnpm dev          # api needs ANTHROPIC_API_KEY
node evals/extract-eval.ts --report /tmp/extract.json
```

Fixtures are other people's menus, so they are not in the repository — see
[evals/fixtures/README.md](../evals/fixtures/README.md).

### Change a prompt

Never edit a shipped prompt version. Add `v2.ts` next to it, activate it in `prompts/index.ts`, and
run the eval before and after. The version is recorded on every `ai_usage` row, so regressions can be
traced to the prompt that caused them.
